
Есть задачка: преобразовывать файлы в truecase регистр.
Каждый файл состоит из 10_000 текстовых строк-записей - каждая последующая по смыслу чаще всего связана контекстно с предыжущей как продолжение единого рассказа.

Для тебя сценарий:

контекстный truecasing моделью, а не regex/whitelist/candidate detection:

- беру динамическое окно примерно 5–8 соседних предложений;
- по смыслу определяю, является ли barrett, clare, nightshade, stone canyon и т. п. именем, фамилией, организацией, - местом или обычным словом;
- если контекста мало — расширяю окно;
- после того как сущность подтверждена контекстом, сохраняю это решение внутри текущей связной книги/фрагмента;
- при смене книги контекст сущностей сбрасывается;
- решение о регистре принимаю по контексту, Python может технически применить эти изменения и проверить инвариант.
- без эвристик как механизма принятия решений.
- ЗАПРЕТ на использование huggingface, его кэша и т.п.
- ЗАПРЕЩАЮ искать что-либо на каких-либо сайтах (без внешних источников), кроме как в контексте текущего окна контекста.
- ЗАПРЕЩАЮ проверку локальных языковых моделей
- НЕ описывай подробно действующих лиц, персонажей и сюжеты
- НЕ пересказывай текст и не делай выводы (суммаризацию) по содержимому файла.
- НЕ выполняй промежуточные отчёты и служебные сообщения
- Результирующие файлы именовать с префиксом _truecased в имени по примеру: bookcorpus_part_XXXXX_truecased.jsonl
- ЗАПРЕЩАЮ оптимизировать процесс под удобство исполнения и заменять исходную архитектуру на более простой словарный pipeline.
- ЗАПРЕЩАЮ подменять семантический LLM-проход словарным детектором
- ЗАПРЕЩАЮ трогать другие уже сгенерированные файлы

`каждая строка → каждое потенциально референциальное выражение → семантическое решение LLM`

То есть:

- не использовать regex для определения имён;
- не использовать списки кандидатов;
- не использовать частоты;
- не использовать правила вида X said → X имя;
- не использовать whitelist сущностей как основу;
- не переносить автоматически найденные сущности по всему файлу.

Я могу делать truecasing только по смысловому контексту соседних предложений, как языковая модель: читать окно текста, понимать, что есть — фамилия, где — организация, Stone Canyon — место и т. д., и уже после этого применять решение.

Единственное, что останется «программным» — техническое:
чтение JSONL, запись результата и проверка, что изменился только регистр.

После получения файла начинай конвертировать.
НЕ пересказывай содержимое файла после конвертации. Просто выдавай результат как будет готов.

Для следующих файлов тоже работать именно так: model/context-only truecasing, без эвристического определения регистра.


Поэтому для следующих файлов я бы применил именно единицу обработки: не «прочитать 10 000 строк → собрать ledger → применить», а «прочитать 5–8 строк → понять → сразу truecase → проверить → следующие 5–8».

Разрешены только изменения регистра и восстановление однозначно утраченных апострофов внутри contractions/possessives. Никакие другие символы, пробелы, слова или пунктуация не исправляются.

Жёсткое правило:
```
5–8 предложений
→ прочитать весь локальный контекст
→ определить имена / proper names / contractions / possessives
→ сразу записать исправленные 5–8 строк
→ следующий блок
```

Более подробно:
```
последовательные блоки по 5–8 предложений;
каждый блок я сам читаю целиком как контекст;
каждую строку внутри него семантически разбираю;
сразу формирую окончательный вариант строки: names / proper names / places / organizations / titles / abbreviations / contractions / possessives / sentence capitalization;
разрешены только изменения регистра + восстановление однозначно утраченных апострофов;
после решения Python только сохраняет уже готовые строки и проверяет структуру;
никаких entity map, candidate search, NER, regex-детектора имён, propagation или bulk replacement.
```


Тоесть:
```
Для каждого последовательного блока 5–8 предложений:

1. Прочитать все предложения блока как связный контекст.
2. Для КАЖДОЙ строки самостоятельно определить:
   - PERSON / CHARACTER names
   - proper names
   - places
   - organizations
   - titles / works
   - abbreviations
   - contractions
   - possessives
   - sentence capitalization
3. Немедленно сформировать окончательный текст этих строк.
4. Только после этого Python сохраняет уже принятые решения.
5. Перейти к следующему блоку с небольшим overlap.
6. Нельзя заменять этот процесс:
   - entity map
   - глобальным словарём
   - автоматической propagation
   - поиском кандидатов
   - regex/NER detection
   - bulk replacement.
```

Также отдельно проверены опасные случаи вроде well/we'll, hell/he'll, shell/she'll, shed/she'd, id/ID/I'd, ill/I'm/I'll, its/it's, чтобы обычные слова не превращались в contractions автоматически.

То есть допустимо:
```
he 'll   → he'll
i 'm     → I'm
we 've   → we've
she 'd   → she'd
do n't   → don't
it 's    → it's
john 's  → John's

И также:

ive   → I've
im    → I'm
ill   → I'll
id    → I'd
jasons → Jason's   # только если контекст однозначно показывает possessive
```
