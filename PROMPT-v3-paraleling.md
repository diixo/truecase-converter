# Context-only truecasing JSONL-файла

## Задача

Преобразовать JSONL-файл из 10 000 записей в truecase-регистр.

Разрешено изменять только регистр символов в поле `text`. Порядок записей, `id`, остальные поля и структура JSONL должны остаться неизменными. Исходный и другие ранее созданные файлы не изменять.

Итоговое имя:

```text
bookcorpus_part_XXXXX.jsonl
→ bookcorpus_part_XXXXX_truecased.jsonl
```

## Архитектура обработки

Файл разделить на 100 целевых блоков по 100 последовательных JSONL-записей.

Каждый блок обрабатывать как отдельную stateless-задачу в физически изолированном модельном запросе. В запрос нового блока не передавать предыдущие сообщения, ответы, решения, рассуждения, списки сущностей или другой накопленный контекст.

Запрещено использовать между блоками:

- историю диалога;
- semantic/entity memory;
- entity map, ledger или глобальный словарь;
- решения из ранее обработанных блоков;
- автоматическую propagation регистра.

Недостаточно дать команду «игнорируй историю»: предыдущие сообщения вообще не должны входить в модельный запрос. Независимые блоки разрешено обрабатывать параллельно.

## Изолированное окно

Один запрос содержит:

```text
context_before: до 5 записей перед блоком
target:         100 целевых записей
context_after:  до 5 записей после блока
```

`context_before` и `context_after` используются только для понимания `target`. Они не исправляются и не включаются в результат блока. На границах файла контекст может быть короче или отсутствовать.

Если окна `5 + 100 + 5` недостаточно, не угадывать. Вернуть внутренний статус:

```json
{"status":"needs_context","ids":[123,124]}
```

После этого повторить только данный блок в новом stateless-запросе с дополнительными соседними записями. Историю других запросов и накопленную память в него не включать.

## Семантический проход LLM

Прочитать всё изолированное окно как локальный контекст. Для каждой записи из `target` самостоятельно определить:

- PERSON / CHARACTER names, фамилии и прозвища;
- proper names, места и географические названия;
- организации, группы и органы власти;
- названия произведений, кораблей, устройств и других именованных объектов;
- титулы и формы обращения;
- аббревиатуры;
- contractions и possessives;
- начала новых предложений внутри записи;
- другие случаи, где регистр определяется смыслом.

Каждое потенциально референциальное выражение оценивается по контексту текущего окна. Одинаковое слово в другом блоке получает полностью независимое решение.

## Запрещено

Нельзя использовать как механизм определения регистра:

- regex или NER для поиска сущностей;
- whitelist, blacklist, candidate list или частоты;
- правила вида `X said → X является именем`;
- предварительный поиск совпадений по всему файлу;
- bulk replacement или автоматический перенос решения между записями;
- словарный pipeline вместо семантического LLM-прохода;
- Hugging Face, его модели или кэш;
- локальные языковые модели;
- сайты, поиск в интернете и другие внешние источники.

## Внутренний результат блока

Не генерировать повторно все исходные строки. Возвращать только подтверждённые семантические изменения регистра:

```json
{"id":123,"changes":[{"old":"tamika","new":"Tamika","occurrence":1}]}
```

Правила:

- `old` — точный фрагмент исходного `text`;
- `new` отличается от `old` только регистром;
- `occurrence` — номер точного вхождения `old` в исходной записи, начиная с 1;
- каждое изменяемое вхождение указывается явно;
- записи без семантических изменений не выводятся;
- изменения не должны пересекаться;
- обязательно `len(old) == len(new)` и `old.lower() == new.lower()`.

Статусы `needs_context` и внутренние изменения пользователю не показывать.

## Разрешённая техническая обработка

Python разрешено использовать только чтобы:

1. читать и разделять JSONL на независимые окна;
2. отправлять каждый блок отдельным stateless-запросом;
3. применять LLM-изменения к явно указанным `id` и `occurrence`;
4. переводить первый алфавитный символ записи в верхний регистр;
5. переводить отдельное местоимение `i` в `I`;
6. проверять блоки, объединять их и записывать итоговый файл.

Пункты 4–5 являются детерминированной нормализацией и не используются для поиска сущностей. Формы без апострофа `im`, `ive`, `ill`, `id` автоматически не исправлять: их значение определяет LLM по контексту.

## Проверка

Для каждого блока проверить:

- результат содержит только записи из `target`;
- каждый `old` существует в указанном `occurrence`;
- изменения не пересекаются и затрагивают только регистр;
- контекстные записи не попали в результат.

После объединения проверить:

- ровно 10 000 валидных JSONL-записей;
- порядок и значения `id` совпадают с исходником;
- все поля, кроме `text`, неизменны;
- длина каждого `text` неизменна;
- `output_text.lower() == input_text.lower()` для каждой записи.

## Поведение

- После получения файла сразу начать обработку.
- Не описывать персонажей и сюжет, не пересказывать и не суммаризировать текст.
- Не публиковать промежуточные отчёты, служебные сообщения, внутренние решения или списки сущностей.
- Пользователю вернуть только один готовый файл `*_truecased.jsonl`.
